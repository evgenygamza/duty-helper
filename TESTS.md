# Проверки

Что и как проверено. Пополняется по мере работы: сделали кусок — здесь
появляется проверка и её результат.

Всё прогоняется руками. Автоматических тестов нет: почти каждая проверка это
разговор с живым Slack и живой моделью. Превращать их в скрипт имеет смысл,
когда набор устоится.

`#channel-with-bot` `C0BSKTQ1M5G`, `#channel-without-bot` `C0BTSTZ2J3X`,
`#duty-feed` `C0BTQL7AK4K`, доска `F0BU23Y14PQ`.

воркспейс `T0BU98BAB5J`: `#channel-with-bot` `C0BU5TL051Q`, `#duty-feed`
`C0BU7RTJCDP`, доска `F0BU1P86005`, группа `S0BV0EVS7ME`.

## Что выяснили про API

Не проверки по плану, а то, обо что стукнулись. Первые строки про песочницу
`sandbox-d879184`, дальше про `duty-helper`.

Приложение `duty-helper`, бот `dutyhelper` (`U0BS4J84MMM`),
группа `@qa-factset-dutyman` = `S0BTF0KMJV6`.
Каналы: `#channel-with-bot` `C0BSKTQ1M5G`, `#channel-without-bot` `C0BTSTZ2J3X`,
`#duty-feed` `C0BTQL7AK4K`.
- поиск группы работает, если в запросе есть `@`: `@qa-factset-dutyman`
  находит настоящие теги `<!subteam^ID>`, без `@` — только текстовые вхождения
- user-токен читает тред в канале, где бота нет: `conversations.replies`
  отдаёт все сообщения, бот-токен там получает `not_in_channel`
- поиск находит призыв из канала без бота примерно через 20 секунд —
  индекс отстаёт, но незначительно
- доска прибивается вкладкой через `bookmarks.add` с `type=link`
- `channels:leave` у ботов не бывает: приложение не может выйти из канала.
  Канал без бота создаётся user-токеном с правом `channels:write`
- подписка на `app_mention` требует scope `app_mentions:read`, иначе
  `apps.manifest.validate` не пропускает манифест
- манифест берётся через хук `get-manifest` из `.slack/hooks.json`; хук по
  умолчанию ищет файл `manifest.json`
- работают `chat.update`, `chat.delete`, `reactions.add/remove`,
  `slackLists.create`, `items.create`, `items.list`, `items.info`
- ячейка в `initial_fields` адресуется через `column_id`, а не через `key` —
  отсюда `invalid_arguments` 25.08. `key` работает только на чтение
- `slackLists.info` не существует; схему списка отдаёт `files.info`,
  id списка это id файла
- `slackLists.update` принимает `id`, а не `list_id`, и меняет только имя,
  описание и `todo_mode`. Колонки задаются **только при создании**
- типы `todo_due_date`, `todo_assignee`, `todo_completed` в свою схему
  не принимаются, и `todo_mode` при создании со схемой не сочетается.
  Но `todo_mode` включается у готового списка и добавляет их поверх —
  так получаются и свои статусы, и родная Due Date
- API для вьюх нет: `slackLists.views.*` — `unknown_method`
- у ячейки нет пометки, кто её правил: `updated_by` один на всю запись,
  поэтому правку текста от смены статуса не отличить
- `todo_due_date` принимает только дату (`2026-09-02`), unix-время — нет
- **бесплатный тир Gemini: 20 запросов в минуту, а не в сутки.** Тело `429`
  называет метрику прямо: `generate_content_free_tier_requests, limit: 20,
  model: gemini-3.6-flash`, и просит `Please retry in 3s`. Проверено по логу
  01.09: отказ в 19:06:45, успешный вызов в 19:06:53, через восемь секунд.
  Суточного предела в логах не видно вовсе, а таблицу лимитов Google больше
  не публикует — своё число видно только в AI Studio. На Claude это будет
  расход, а не отказ:
  вызов на реальном треде ≈ 0.012$ на Opus 5, то есть 5$ ≈ 400 обращений
- сабтаски есть: `items.create` с `parent_item_id`, у родителя приходят
  в поле `subtasks`. Схема у сабтаска та же, значит свой статус и свой срок
- в ячейку кладётся полноценный rich text: абзацы и маркированные списки
- `slackLists.items.update` работает через `cells`:
  `[{row_id, column_id, <тип>}]`. Это и была причина `invalid_arguments`
- методов `slackLists` ровно двенадцать, работы с обсуждением среди них нет —
  но комментарии ловятся событиями, см. ниже
- **пермалинк непостоянен**: у сообщения без ответов один адрес, у того же
  сообщения с ответами — с хвостом `?thread_ts=&cid=`. Сравнивать треды
  можно только по адресу без параметров
- событие о призыве приходит не мгновенно: наблюдали задержку до 35 секунд
- список, созданный ботом, никому не виден: `channels: []`. Публикация
  ссылки в канал даёт доступ только на чтение. Права раздаёт
  `slackLists.access.set` — `access_level` `read`/`write`/`owner`,
  и либо `channel_ids`, либо `user_ids`, вместе нельзя
- у Gemini таймаут ставится на клиенте (`http_options`), не в вызове;
  `gemini-3.7-flash` на бесплатном тире перегружен, `3.6-flash` отвечает
- **Lists не рождают файловых событий.** `file_change` не приходит ни на смену
  статуса, ни на правку текста карточки, ни на переименование самого списка.
  Проверено с контролем: подписка есть на стороне Slack (`manifest info`:
  `file_change` в `bot_events`), бот владелец файла (`access: owner`), список
  расшарен в `#duty-feed` с `write`, бот в канале состоит, и за десять секунд
  до переименования в тот же сокет доехали два обычных `message`
- **бот не может написать в личку, пока у приложения выключена вкладка
  «Сообщения»**: `chat.postMessage` в диалог отвечает `messages_tab_disabled`.
  Лечится блоком `app_home` в манифесте, `messages_tab_enabled: true`.
  Права `im:write` для этого недостаточно
- custom step в Bolt Python: блок `functions` в манифесте, подписка
  `function_executed`, `@app.function(...)`, завершение через `complete()`
  или `fail()`. Записано на случай, если выброшенный шаг понадобится снова
- **custom steps требуют платного тарифа.** Один и тот же манифест с блоком
  `functions`: на `duty-helper` `E0BU1D8791B` (Enterprise sandbox) —
  `Valid`, на `sandbox-d879184` `T0BSDLTDKBM` (Free) —
  `free_team_not_allowed` на `/settings/function_runtime`. Плюс схема требует
  `function_runtime: remote` и `org_deploy_enabled: true`
- `slack sandbox create` отвечает `invalid_access`, пока аккаунт не в Slack
  Developer Program. После регистрации создаётся сразу
- автоматизации списков в песочнице **есть**, несмотря на бесплатный тариф:
  панель Workflows у списка даёт шаблон «Channel alerts about updated items»
  и «Build your own in workflow builder». Отказ `free_team_not_allowed`
  у `apps.activities.list` — про платформу разработчика, не про Workflow Builder
- `files.info` по списку отдаёт `updated`, `edit_timestamp` и `last_editor`
  одним вызовом. Дёргается на правку текста карточки и на переименование
  списка; на чистую смену статуса не проверялось
- **комментарий к карточке доходит до бота обычным событием `message`.**
  Проверено 04.09. Беседа списка — это его id с `F` на `C`: доска
  `F0BU1P86005` → канал `C0BU1P86005`, `channel_type: group`. У каждой
  карточки там свой тред, родитель — сообщение Slackbot с подтипом
  `list_record_comment` и текстом «A comment was added». Связь тред → карточка
  лежит в родителе: `slack_list: {list_id, list_record_id}`.
  Само событие комментария подтипа не имеет.
  `items.info` при этом про обсуждение не знает: отдаёт только поля записи
- **смена статуса карточки событий не рождает** — проверено на Enterprise-
  песочнице с логгером сырых событий: статус двинут, в логе тишина.
  Для реакции на статус нужен воркфлоу
- лог бота при перенаправлении в файл **буферизуется блоками** и отстаёт
  на минуты: запускать с `PYTHONUNBUFFERED=1`, иначе живой бот выглядит мёртвым
- **слаковские `ts` всегда кончаются на 9.** Любой выбор через `int(ts) % N`
  берёт только нечётные остатки: при восьми вариантах четыре недостижимы
- `conversations.history` отдаёт **только верхний уровень**: сообщение,
  написанное ответом в треде, через неё не найти
- `conversations.replies` за один запрос отдаёт и сообщения треда,
  и реакции на каждом из них
- у новых приложений вне Marketplace `conversations.replies`
  и `conversations.history` с 29.05.2025 ограничены 1 запросом в минуту
  и `limit` 15. На наше не действует: восемь вызовов подряд прошли,
  `limit=200` не урезан. Причина, скорее всего, в том что оно внутреннее
- при установке на орг методам нужен `team_id`: `users.conversations`,
  `usergroups.list` и `search.messages` без него отвечают `missing_argument`,
  а с `team_id` **орга** — `team_access_not_granted`, нужен именно воркспейс.
  `auth.test` отдаёт только enterprise, воркспейс знает канал —
  `conversations.info` → `context_team_id`
- **user-токен в канале без бота делает всё**: находит поиском, читает тред
  и ставит отметку. Отметка появляется от лица человека, поэтому «свои»
  отметки надо узнавать по двум личностям
- CLI хранит только `xoxe.` — служебный токен для управления приложением,
  для `search.messages` он бесполезен. У локального приложения на странице
  OAuth токенов нет вовсе, они на отдельной «Install App»
- `slackLists.delete` не существует; список удаляется `files.delete`
- пересоздание доски **ломает воркфлоу**: его триггер привязан к списку
- `bookmarks.add` работает, а `bookmarks.list` боту показывает пустой список
- `assistant.search.context` → `invalid_action_token`: метод для ассистентов
  Slack, не наш путь
- **воркфлоу через API не создаётся вовсе.** В справочнике методов есть
  `admin.workflows.search`, `unpublish`, `collaborators.*` и `permissions.*`,
  и ни `create`, ни `update`. Workflow Builder к тому же не принимает готовый
  воркфлоу кодом: вносится только custom step отдельным шагом
- `admin.*` ботовым токеном не ходит: `not_allowed_token_type`. Юзерским
  отвечает `missing_scope, needed: admin.workflows:read`. В песочнице скоуп
  дать можно, владелец токена `is_primary_owner`, но на проде его не будет,

- **у опубликованного воркфлоу триггер не меняется**: справка Slack предлагает
  копию с новым триггером. Отсюда и невозможность перенаправить его
  на новую доску
- **API листов ничем не огорожено**: двенадцать методов `slackLists.*` без

  на Pro и Business+, до 5000 на Grid
- `slackLists.download.start` и `download.get` выгружают содержимое листа.
  Пригодится при очередном пересоздании доски: это копия старой, не перенос

## Чего не проверяли

- поведение на **реальных** тредах: длинных, с curl-выводами, простынями ISIN
  и размытыми формулировками
- **замок на тред под нагрузкой**: код есть, но одновременного обращения
  события и обхода к одной карточке мы не воспроизводили
- надёжность воркфлоу: сколько изменений он теряет, если менять статус часто
- комментарии как канал связи: бот их слышит, но ничего с ними не делает
- что будет, когда карточек станет больше сотни: `items.list` берётся
  с `limit=100`, дальше нужна страничная выборка
- одновременные призывы в разных тредах
- поведение после перезапуска бота: пропущенное за простой не добирается
- права и поведение в рабочем воркспейсе — там другое приложение
- **`/duty` живьём**: слэш-команду через API не позвать, её надо набрать
  в Slack. Проверены разбор, фолбэк и регистрация; сама команда набиралась
  10.09 и нашла ошибку в фолбэке, после правки заново не набиралась
- **`/duty @имя` целиком**: право на запись есть и проверено на API, но сама
  команда живьём не набиралась
- точность «В статусе с» после переезда в обход: время ставится с точностью
  до одного прохода, на пороги Э7 это влиять не должно, но не мерялось
- **права приложения на листы в рабочем воркспейсе**: `lists:read`
  и `lists:write` проверяются только установкой
- доступны ли custom steps на платном не-Grid воркспейсе: на бесплатном отказ
  проверен, на Enterprise работает, середина не смотрелась
