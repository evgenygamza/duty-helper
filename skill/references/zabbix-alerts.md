# Разбор Zabbix-алертов (ветка сервисов)

Мониторинг основан на реакции на алерты в Slack-каналах из Zabbix. Цель —
своевременно обнаружить, проанализировать и устранить проблему со стабильностью
сервисов. Большинство алертов с **auto-recovery** и закрываются сами.

## Каналы алертов

| Канал | ID | Что |
|---|---|---|
| #factset-disasters-prod | `C05MSPMHZU1` | прод (hub4/hub3), все сервисы |
| #factset-disasters-stable | `C090B08AGPK` | stable (hub01), все сервисы |
| #factset-loaders-disasters-staging | (искать) | staging, только factset-loader (критичен для стендов) |
| #factset-disasters (архив) | (искать) | staging, история — НЕ мониторить постоянно |
| #factset-ipo-alerts | (искать) | IPO-коллизии |
| #factset-data-checker-prod / -staging | `C072Z0Q8NDU` (staging) | symbolinfo-provider + MR-ы enum-registry |
| #zabbix-disasters / #zabbix-alerts | `C8VH5S0AJ` / `C5P7ADW11` | общий поток алертов |

Тексты алертов в блоках: в **поиске** (`slack_search_*`) поле Text пустое, но при
**чтении канала** `slack_read_channel` с `response_format=detailed` блоки
рендерятся полностью (триггер, host, opdata, ранбук, «Response: qa_factset») —
это основной способ читать алерты.

**Но поток алертов в ответ не помещается.** Пятнадцать минут `#zabbix-disasters`
— это ~79k символов в `detailed` и ~60k в `concise`, оба раза результат уходит в
файл вместо ответа (проверено 21.08.2026). Переключаться на `concise` бесполезно:
у Zabbix он печатает тот же ранбук целиком. Поэтому не подгоняй окно под лимит, а
сразу разбирай дамп парсером:

```
python3 scripts/parse_alerts.py <файл-с-выводом>
```

Парсер делает дедуп по `triggerid` (правила ниже) и печатает открытые, флап и
закрывшиеся отдельно. Он же принимает поток на stdin, если вывод пришёл целиком.

## Дедуп по triggerid (обязательно)

Один инцидент = десятки сообщений. У каждого алерта в ссылке есть `triggerid=NNN`
и `eventid=MMM`. Правила схлопывания:

- Группируй по `triggerid`. Пары `:exclamation:` (проблема) и
  `:heavy_check_mark_green:` (recovery) с одним eventid — это открытие/закрытие
  одного события.
- **Открытый инцидент** = у триггера последнее по времени состояние `:exclamation:`
  без последующего green. Только такие идут в 🔴/🟡 дайджеста.
- **Флап** = много пар problem→recovery подряд у одного triggerid (auto-recovery
  срабатывает). Сворачивай в ОДНУ строку: «`<триггер>` на `<host>` — флапает,
  N срабатываний за период, auto-recovery». Не спамь построчно.
- `opdata` в алерте = число проблемных объектов (0 при recovery).

Пример с живого прогона 2026-07-21: `Schedule executor failed` (triggerid
24411704/24411705) флапал парами → одна строка; а `entity failed` (52632324),
`entity publish blocked` (78313738), `bond publish blocked` (78313735) на
hub4-factset-snapshots — открытые, без green → реальный сигнал.

## Как обрабатывать алерт

1. **В начале дня** — разобрать всё, что упало ночью/в выходные. В течение дня —
   следить за новыми.
2. Ориентируйся на **ранбук из секции `description`** алерта.
3. Работа по инциденту (расследование, коммуникация, эскалации) — **в треде**
   сообщения в Slack.
4. Реакции:
   - :eyes: — взял в анализ
   - :acknowledged: — обработал (завершение)
5. Каждый обработанный алерт = **артефакт**: коммент дежурного, ссылка на Jira
   или тред с разработчиками. Если проблема известна — ссылка на существующий тикет.
6. Эскалация — `@factset-dev` (в `#team-factset-internal`).

### Первичная диагностика (общие советы)

- Проверь, не ведёт ли кто работы с сервисом/зависимостями (см. `#deploy`,
  `#announcements`) — возможно забыли maintenance.
- Не связана ли проблема с доставкой метрик (обрывы, контейнер потух, хост
  перезагружается) — смотри последние значения метрики в Zabbix.
- Прочти `description` триггера — что случилось, что делать, кого звать.
- Логи: ридми контейнера в репе `tv/docker` или дашборд logviewer
  (`dashboard.xtools.tv/dashboard-prod/#/logviewer2`).
- Slack как «маленький гугл» — ищи по названию триггера в истории, скорее всего
  уже было.

## Спецкейсы (ручная работа)

### Snapshot Datacheck failed — ТРЕБУЕТ ручного закрытия в Zabbix

Причина — некорректные данные от FactSet. Auto-recovery НЕ срабатывает.
1. Анализ проблемных символов.
2. При необходимости — письмо в FactSet через issue tracker.
3. Правка rulesets в `symlistfeed-preprocessor` или расширение ignore-секции.
   **Менять сразу для prod, stable И staging.**
4. Ручное закрытие: Zabbix → сервис → вкладка *Problems* → найти *Snapshots
   datacheck failed* → галка → *Mass update* → *Close problem* → *Update*.

Алерт задедуплицирован — включён только для prod (иначе дублируется по всем хостам
factset-snapshots).

### Обновление enum-registry (нотификации в #factset-data-checker-*)

**stage / stable:** открыть МР → правки в web-IDE в `enums/bond_issuer.yaml` и
`enums/bond_issuer_cr_parent.yaml` (не затирать существующее, новые значения
валидны) → коммит и мердж → в конце красного пайплайна будет ссылка на МР команды
nova → мерджим как есть.

**prod:** прав на мердж в продовый enum novы нет — просить в `#team-nova`
(`C06M0NHDUN6`).

## Историческая аналитика алертов

Цель — понять, **новый ли это инцидент или рецидив**: как часто триггер падал
раньше, всегда ли auto-recovery, кто и как разбирал в прошлый раз.

Шаги:

1. **Взять «отпечаток» триггера** из текущего алерта: название (напр.
   `entity publish blocked`), host (`hub4-factset-snapshots`), при наличии
   `triggerid`. Название триггера стабильно между срабатываниями — по нему и ищем.

2. **История в канале алертов.** ВАЖНО: текст бот-алертов лежит в блоках и
   **не индексируется полнотекстово** — поиск `"<название триггера>"` по каналу
   алертов вернёт почти пусто. Поэтому историю бери двумя способами:
   - `slack_read_channel` с временным окном `oldest`/`latest` (Unix ts) —
     перебрать сообщения канала за период и посчитать срабатывания триггера по
     `triggerid` (см. дедуп выше): регулярный флап vs редкий инцидент, всегда ли
     рядом `:heavy_check_mark_green:`.
   - **Zabbix по triggerid** (`tr_events.php?triggerid=NNN`) — самая точная
     история именно этого триггера. Предпочтительно, если нужна частота.

3. **Как разбирали раньше** — вот это через поиск работает хорошо, т.к. люди
   пишут название триггера/host текстом. Ищи обсуждения:
   ```
   "publish blocked" -from:USTHVD1GT after:<дата>
   "<host>" in:#team-factset-internal
   ```
   в `#team-factset-internal`, `#backend`, `#deploy` — там тред с разбором и,
   как правило, ссылка на Jira/ITSM-тикет (пример: живой прогон 2026-07-21 нашёл
   ITSM-71543 / ITSM-71546 по `bond publish blocked` — рецидив известного инцидента).

4. **Своя хроника** — параллельно `python3 cases/search_cases.py "<триггер host сервис>"`:
   если инцидент уже заносили, увидим прошлое решение и Jira.

5. **Вывод** для дайджеста: «триггер X на host Y — N-е срабатывание за месяц,
   ранее всегда auto-recovery / ранее разбирали в {тред}, чинили {как}» либо
   «раньше не встречалось — новый инцидент».

Совет: по `triggerid` в Zabbix (`tr_events.php?triggerid=NNN`) можно открыть
полную историю событий именно этого триггера — точнее, чем поиск по тексту.
